## Actual registration and lifecycle

- `cms/conf.py:Config._load_unique` expands configured `core_services`/`other_services` into `ServiceCoord` to `Address`; arbitrary service names are supported, no task-plugin registration involved.
- `cms/io/service.py:Service.__init__` derives coordinates from class name/shard, sets signal handlers and RPC StreamServer. `initialize_logging` creates per-coordinate file/last.log and forwards to LogService. `run`, `exit`, RPC echo/quit provide lifecycle.
- `cms/io/web_service.py:WebService` wraps Tornado WSGIApplication with file/static middleware and a gevent WSGIServer. HTTP listener and Service RPC listener are distinct. The current ProxyFix trusts forwarded addresses solely by configured hop count, requiring trusted ingress/network exclusion.
- `cms/util.py:default_argument_parser` accepts optional shard and `-c/--contest-id`; `contest_id_from_args` supports `ALL` or a verified DB contest ID. All services accept `-c` because ResourceService always supplies it.
- `cms/service/ResourceService.py:ProcessMatcher._is_interesting_command_line` recognizes installed `cms[A-Za-z]+` scripts under BIN_PATH and Python command lines. `OlympiadIDEService` matches without adding an allowlist. `_find_local_services` selects coordinates whose configured address IP matches ResourceService's. `_restart_services` skips only LogService, ResourceService and contestless ProxyService, detects existing processes, and launches `<BIN_PATH>/cms<Service> <shard> -c <id|ALL>` every five seconds when absent. No restart bound exists upstream. `toggle_autorestart` plus `kill_service` implement intentional stop/restart controls.
- `cms/service/Checker.py:Checker.__init__` connects to all configured core services; no new registration list is needed. Admin `cms/server/admin/templates/resources.html` renders ResourceService's generic service dictionary and restart controls.
- `setup.py` uses `find_packages`, explicit launcher `scripts`, and explicit package-data glob lists. New launcher and optional installed assets must be registered; Node build must remain opt-in.

## Actual authentication/context

- `cms/server/contest/server.py:ContestWebServer` uses `hex_to_bin(config.secret_key)` as Tornado cookie secret and `xsrf_cookies=True`. It sets contest_id, translations, CWS Jinja environment, and evaluation/scoring/proxy/printing RPC clients.
- `cms/server/contest/handlers/contest.py:ContestHandler.prepare/choose_contest/get_current_user/render_params` performs DB contest selection, authenticates to a Participation, computes participant timing, and prepares policy state. The native service will reuse it with one explicit contest ID. Multi-contest native startup will fail explicitly in this slice.
- `cms/server/contest/authentication.py:authenticate_request` rechecks contest membership, password-cookie validity, configured IP autologin, restrictions, and hidden participation blocking. Cookie name is `<contest.name>_login`; Tornado signing wraps the serialized username/password-hash/update timestamp. Username is lookup-only; IDE principal ownership will use stable numeric IDs. Native code must never pass the cookie/password representation to the private runtime.
- `LoginHandler` and `LogoutHandler` in `handlers/main.py` set/clear the signed login cookie with default path `/`. Login is POST through existing CWS; no new password store or proxy password endpoint is required.
- `CommonRequestHandler` in `cms/server/util.py` owns one request timestamp and SQLAlchemy session, closing it in `finish`. Polling handlers should not refresh the login cookie, matching `NotificationsHandler.refresh_cookie=False`; runtime gateway must close its CMS session before waiting on private HTTP.
- `compute_actual_phase` in `cms/server/contest/phase_management.py` accounts for contest timing, per-user start, delay, extra time and analysis. `actual_phase_required(0,3)` also permits unrestricted participants. Context can be returned in every authenticated phase, but tasks/assets are only exposed when the same CWS visibility gate permits them.
- `handlers/task.py` guards statements and attachments with authentication, phase, contest/task membership, and only task.statements/task.attachments lookup. Native context should link to those CWS routes, never inspect or export judge managers/testcases.
- Task ordering is `Contest.tasks` via ordering_list(num). Official language identifiers are `Language.name` strings (e.g. `C++17 / g++`), filtered by contest.languages and the actual task type's compilation commands. These differ from IDE execution profile keys.

## Agreed integration surface

Static `/ide/`; bootstrap `/ide/api/context`; private runtime gateway `/ide/api/runtime/v1/<existing backend suffix>`; official `/ide/api/submissions`. JSON contracts carry schemaVersion 1. Every protected request reuses CMS authentication. Requests except bootstrap carry `X-Olympiad-Principal`, checked against a server-derived UUIDv5(URL namespace, compact ASCII JSON array of installation/user/contest/participation ID strings) to detect account changes before uploads. No browser owner IDs authorize access.

Native service owns logging/RPC/HTTP/auth/context/admission. ResourceService owns only native CMS process; systemd owns private ASGI runtime and isolated custom-run worker separately. The native service does not launch participant programs or supervise an unrelated website. CMS evaluation/judging ownership remains unchanged.

This report is source-audit evidence, not a lifecycle, auth, judging, Linux execution or capacity test result. Implementation and concrete verification are recorded separately.

## Implemented contract and transaction boundary

Implementation uses `cms/server/olympiadide/admission.py:prepare_intent/admit_intent/receipt_view/notify_after_commit`, `handlers.py`, `cms/server/contest/submission/policy.py`, and the existing `workflow.py:accept_submission`. CWS SubmitHandler calls the same new outer operation, and all paths through the existing admission operation acquire the same PostgreSQL participation `FOR NO KEY UPDATE` lock. This serializes count and interval checks across native service shards, CWS, and simultaneous requests without a second quota counter.

Official API is `/ide/api/submissions` POST, GET history with `taskId` and bounded `offset`; `/ide/api/submissions/<intent UUID>` GET; `/ide/api/submissions/status/<opaque CMS id>?taskId=...` GET. CMS JSON has `schemaVersion:1`. POST request fields are exactly `schemaVersion,intentId,taskId,language,files,snapshotId,workspaceId,telemetry?`; each selected file has exactly `filename,sourceFilename,fileId,content`. `filename` is the actual CMS submission-format schema (for example `main.%l`); `sourceFilename` is the selected source basename and must match the chosen CMS language extension. Browser-supplied ownership, official flags, timestamps and override parameters are rejected.

`prepare_intent` rejects unpaired surrogates, enforces the actual CMS per-file byte bound and an additional 8 MB total source bound, hashes exact UTF-8 bytes, and computes normalized immutable input before the participation lock. Scope and the normalized request—including task, language, filenames and source strings—form the canonical SHA-256 request digest. The caller supplies only authenticated CMS participation and current server timestamp. Within the lock a matching committed intent returns its original receipt before phase/capability checks; changing its immutable request returns HTTP409 `intent_reused`. A new intent must pass current timing/capability/mapping and the same CMS count/interval/size/language/source-storage policy. Distinct intent IDs intentionally allow identical source.

Submission/File relationships and `OlympiadIDEReceipt` are inserted in the same CMS SQL transaction. The handler materializes the receipt, commits, then invokes `EvaluationService.new_submission` as a best-effort hint. It returns201 only after commit, or200 for a matching committed retry. An exception during/at commit produces an unknown result (generic safe500), never an invented receipt. The original CMS EvaluationService sweeper (117s) discovers required operations from durable Submission rows; its queue/cache/execution deduplication handles repeated hints. No cross-database transaction or official source dependency on IDE storage, telemetry, or custom Run exists.

`receivedAt` deliberately retains pinned CMS request-time semantics: it is `CommonRequestHandler.timestamp`, the server timestamp established when the CMS handler prepares the request, reused for policy checks and Submission.timestamp. Hash/admission/commit occur later and are not represented as an earlier deadline reservation. There is no new client clock authority or admission-time reinterpretation. Offline local capture remains unconfirmed until CMS admission. A stored receipt lookup is phase-independent but authenticated/owned. History and fresh feedback preserve normal phase access. Manual official POST refreshes the CMS login cookie as CWS Submit does; background history/receipt/status/context/runtime calls do not extend idle auth.

## Feedback and fallback

`cms/server/contest/submission/feedback.py` extracts the pinned CWS participant serializers; CWS status/details and native feedback now call that same policy. It uses the current active dataset on every request, public/full score separation, tokens and analysis, partial aggregate scores, configured precision and existing CMS state labels. `cms/server/olympiadide/feedback.py` converts only already policy-filtered score-plugin HTML into inert bounded text and supplies permitted compiler messages/stdout/stderr with explicit truncation markers. React does not receive raw private score-details JSON or HTML to execute. Ownership is checked before every external-id lookup. Native receipts retain a stable opaque CMS encrypted identifier; lookup resolves it through the owned receipt relationship before decrypting ordinary CWS ids, so a logical CMS dump import's changed DB ids cannot redirect a saved native identifier to another submission.

The first official slice accepts standalone Batch with one source `%l` format. File-I/O standalone Batch can be officially admitted because CMS owns its actual judge I/O. Custom Run is separately limited by context/gateway to standalone stdin/stdout Batch. Grader-based Batch, arbitrary multi-file formats, OutputOnly and Communication/interactive workflows are explicitly unsupported in the IDE and retain normal CWS links. Native history includes ordinary CWS submissions with null IDE correlation; no fabricated workspace/telemetry link is created.

## Additive schema and restoration

`cms/db/olympiadide.py:OlympiadIDEReceipt` adds only `olympiad_ide_receipts`: unique `(installation_id,participation_id,intent_id)`, unique submission FK and opaque external id, request digest, manifest with SHA256/size/source-file identity, original identity scope, workspace/snapshot/telemetry correlation, receipt time. Submission has a lazy receipt relationship so a feature-disabled old CWS operation does not require this optional table. `cms/db/__init__.py` dump model version is45; `cmscontrib/updaters/update_45.py` adds the empty receipt backreference to v44 submission dumps. CMS product version remains1.5.1.

`cmsOlympiadIDEMigrate --dry-run` is the default and reports `would_create` or `already_present`; `--apply` creates only this table and its constraints through the actual SQLAlchemy metadata create mechanism used by CMS. An advisory transaction lock serializes installers. Existing schema column/unique-constraint mismatches fail closed. It never drops/resets/alters core tables, runs no IDE Alembic on CMS metadata, and is not invoked at startup. Feature rollback disables service without deleting receipts. Production application requires a verified CMS backup and explicit operator execution, not the unit-test reset fixture.

Real DumpExporter/Importer coverage proves receipt relationship, opaque id, scope/hash/correlation and actual DBBackend source bytes survive CMS logical export/import. Standard CMS logical import can remap numeric user/contest/participation/submission ids; original stored scope stays provenance, while runtime principal identity deliberately changes and must not silently adopt prior runtime data. For exact identity-preserving disaster recovery use matched physical PostgreSQL backups and original installation/configuration secrets, as documented by root. Restoration/adoption across remapped logical identities is an explicit follow-up migration/reconciliation task, not an automatic trust transfer.
