## Verified existing behavior and relevant symbols

- `backend/app/main.py:create_app` installs all persistence, telemetry and execution routes. Its nested `identity` (line 56) validates a random development bearer cookie by SHA-256 token hash and expiry. `COOKIE` is `olympiad_session`; `/api/v1/session` (line 72) creates a 30-day development identity when no valid cookie exists. The cookie is HttpOnly, SameSite Strict, path `/api`, with Secure controlled by `COOKIE_SECURE` (default false). There is no CMS mode, CMS session validation or private-call authentication.
- `backend/app/models.py:DevelopmentIdentity` (line 13) is the authority table. Workspace, synchronization operation, telemetry session, execution job and resource-receipt ownership foreign keys point to it. Replacing cookie authority alone would not supply installation/contest/participation binding, adoption proof, or account-switch protection. These require an additive principal design/migration that preserves existing IDs and quarantines unproven legacy ownership.
- `backend/app/service.py:owned_workspace` (line 23) hides unauthorized/deleted workspaces with 404. `apply_operation` (line 77) locks the workspace, checks identity and immutable operation digest, implements revision CAS, writes source/settings/snapshots/revision/receipt together, and the handler commits before replying. Mutation failure rolls back the whole batch. Existing receipts are workspace persistence receipts, not official CMS submissions.
- `backend/app/telemetry.py:lock_owner`, `ingest`, `replay_at`, `install_routes` preserve owner-scoped quota locking, UTF-16 replay, contiguous sequences, hashes, append-only events, durable chunk ingestion and receipts. `telemetry_schema.py` uses strict discriminated schemas; RUN_STARTED/RUN_FINISHED optionally carry execution correlation, while no official submission events/correlation currently exist. Telemetry must stay separate from workspace and official admission transactions. Browser telemetry remains untrusted observations.
- `backend/app/execution_service.py:submit` (line 62) checks ownership, locks the development owner using `FOR NO KEY UPDATE`, hashes the immutable request, validates the source/configuration digest, and creates the execution snapshot and queued job. A same-ID/same-body retry returns the original job; changed-body retry fails. Default admission is 3 queued and 100 requests/hour/owner. This is custom execution only and must not be mistaken for CMS admission idempotency.
- `execution_service.py:claim` (line 132) uses a short PostgreSQL advisory transaction lock, SKIP LOCKED and active-owner exclusion. `fenced_job` (line 148) validates lease identity and expiry. `expire_leases` (line 117) marks unresolved worker outcomes as infrastructure errors rather than success. `finish` validates results and respects cancellation races.
- `backend/app/execution_api.py` has independent Run/Stop/history/capacity routes. SSE releases its initial checked-out DB connection and uses fresh short transactions per polling iteration (lines 68–93), with bounded stream duration. The background reaper runs every five seconds. Missing fresh worker heartbeats are reflected by capacity; there is no official submission path to be coupled to worker capacity.
- `worker/app/main.py:main` requires Linux sandbox readiness and `WORKER_SANDBOX_APPROVED=1` before claiming jobs. The separate worker uses threaded bounded concurrency, durable leases, periodic heartbeats and cancellation on DB failure. It does not use CMS RPC or CMS ORM. Database privileges must be configured externally; the Python code itself does not create/restrict the DB role.
- `worker/app/sandbox.py:Sandbox` rejects macOS, missing isolate, root worker execution, unsafe helper ownership/mode, absent cgroup v2 and enabled swap. No unrestricted execution fallback exists. Safe artifact reads reject symlinks, nonregular and oversized files. Sandbox initialization supports both isolate root and box-child output; cleanup occurs after invalid path rejection.

## Integration gates and security gaps to resolve in target CMS

1. Actual CMS service registration, session/authentication semantics, IP restrictions, contest phases, quota/admission locks, file formats/languages, receipts, notification recovery and participant feedback serializers cannot be inferred from this IDE tree. Audit the pinned CMS revision before implementing any adapter.
2. The current session endpoint automatically establishes new development authority; CMS mode must fail closed and disable this fallback. A trusted private gateway needs signed/verifiable scoped identity assertions and a narrow allowlist; a hostname or private listener is insufficient.
3. Origin checking currently applies only when an Origin header is present. The request limiter trusts Content-Length and does not independently count streamed body bytes; invalid numeric headers are not handled safely. These are existing development limitations to address within the supplied production ingress/gateway, along with CMS-native CSRF rules, quotas and exception responses.
4. `/api/v1/health` is DB readiness only; independent liveness, runtime readiness and custom-worker degradation need explicit integrated semantics. SQLAlchemy pool settings and ingress budgets are not explicitly capacity-tuned in this tree. No 300–350-participant measurements were made.
5. Official admission must have its own immutable source-byte manifest and CMS-transaction receipt; the existing custom job UUID/hash does not satisfy that guarantee. Keep Run/Stop and official Submit distinct and preserve custom queue fencing/limits independently.
6. CMS user/task/contest tables, hidden judge data and CMS credentials must never enter IDE worker access. Existing execution-only DB role instructions are deployment guidance; verify installed grants in an authorized disposable integration environment.
