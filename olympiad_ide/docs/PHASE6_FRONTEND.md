# Phase 6 — Interactive debugger frontend

The Debug active file action captures the focused editor's exact source through the existing immutable execution snapshot/hash contract. It captures STDIN and the current persisted file-ID breakpoints at that same start boundary. Later edits and best-effort relocated breakpoint lines apply to the next session, not the already captured program. Debugging never selects a legacy Run configuration.

The frontend posts this snapshot to the owned debug-session API. Backend capacity/isolation errors remain explicit failed states rather than simulated execution. The native CMS gateway issues an expiring one-use attach token. The browser opens the exact same-origin DAP WebSocket and sends that token in its first frame; it is never placed in a URL, local storage or log. Every20seconds the frontend requests a fresh token through CMS-authorized HTTP. Authorization failure closes transport, clears paused inspection and shows the failure. Backend owns the stronger disconnect/lease cleanup policy.

Initialization follows real adapter sequencing: initialize response, send launch without awaiting its response, wait for initialized event, set captured breakpoints, configurationDone, then await launch. This avoids debugpy's deferred launch-response deadlock and supports adapters that send initialized early. Every DAP request has a sequence-bound response and bounded timeout. Only the server-allowlisted initialize/launch/breakpoint/control/stack/scope/variable commands are exposed. There is no Evaluate, REPL, shell, arbitrary adapter launch configuration or fake variable state.

The pane contains Start/Stop, Continue/Pause, Step Over/Into/Out, breakpoints, actual adapter breakpoint verification, captured source hash/files, actual stack frames, scope variables with child-reference inspection, and bounded inert text output. Stack/variables only appear after corresponding real DAP responses. Missing thread identity triggers a real threads query; no thread ID or stopped location is fabricated. Global toolbar/Monaco integration is wired by the workbench. Read-only history viewers remain separate from breakpoint editing.

Generation guards fence workspace changes, late old stop responses, old socket events, adapter stop/control-response races and stale frame/variable replies. Newer stopped events win over earlier command acknowledgements. Breakpoints persist in workspace-scoped metadata, keyed by stable file ID, limited to100 lines/file within1–1,000,000. Reload loading rejects invalid entries. Page lifecycle Stop can use keepalive HTTP; transport/worker expiry and disconnect cleanup remain server authority. Existing DEBUG_STARTED/ACTION/FINISHED records use their existing telemetry schema and never collect debugger expression input.

## Verification boundary

Eleven protocol-controller tests passed alongside the twelve Phase5 tests, with full typecheck and zero-warning lint. Controller tests use scripted DAP responses as protocol fixtures: they prove deferred launch ordering, immutable source/breakpoint capture, exact stack/scope/variable handling, stopped-event race fencing, token refresh/auth-expiry closure, old-workspace stop isolation and bounded scoped breakpoint reload, and real thread discovery before Pause when no prior stopped event provided a thread ID. A Pause acknowledgement alone never sets a fake stopped state; the actual stopped event does. They do **not** prove actual debugger binaries or sandbox execution. Real C++/Python/Java adapter and worker verification belongs to the Linux deployment evidence and must pass separately before declaring those languages functional.


Follow-up lifecycle hardening: Stop uses a stopping state, owned POST acknowledgement and bounded owned GET polling until the worker reports a terminal state. Network/authentication failures remain explicitly unconfirmed, not finished. Paused stack/scope/variable inspection keeps step/continue controls disabled until all in-flight reads complete; old inspection replies cannot repopulate new frames. Actual breakpoint-change events update pending/verified locations after adapter symbol loading. Additional tests cover delayed variable reads, stop confirmation/unconfirmed failure and pending-to-verified adapter events. These protocol tests remain separate from the real GDB variables-paging fix and live browser evidence.

GDB inspection collects both Arguments and Locals scopes, retaining scope labels, instead of silently showing only the first scope. Register scopes are excluded. The busy fence remains until all requested scope-variable reads finish. This has a focused regression for a real-shaped separate Arguments/Locals response with result5, alongside deployment-level real adapter tests.
